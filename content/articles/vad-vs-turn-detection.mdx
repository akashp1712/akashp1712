A caller says *"I wanted to, uh —"* and stops for a second to find the word.
Your agent hears 800ms of quiet and starts talking.

Voice activity detection did its job. It reported: speech, then not-speech.
You treated "not-speech" as "your turn." That is the bug. Humans pause inside
turns constantly. The gap between turns in conversation is around 200ms;
the pause *inside* a thought is often longer.

VAD answers a physical question. Turn detection answers a conversational one.
They are not the same model, and LiveKit will not save you if you collapse
them into `if silence > 400ms: reply()`.

## What VAD actually scores

Every 20ms PCM frame from the [WebRTC track](/articles/webrtc-for-voice-agents)
gets a probability: *is this speech-shaped audio?*

Classic energy VAD does this with RMS. If the frame is louder than a
threshold, it is speech. HVAC, a TV in the next room, and a keyboard all
pass. It is cheap and it is wrong in the environments voice agents actually
run — phones, kitchens, cars.

[Silero VAD](https://docs.livekit.io/agents/logic/turns/vad/) is a small ONNX
network trained on speech vs everything else. In LiveKit it is the default
ear for the STT-LLM-TTS pipeline. Typical inference is 15–30ms. That is fast
enough to sit on the media clock. It is also CPU work, which is why LiveKit
does **not** run it on the asyncio loop — more on that in
[part 4](/articles/asyncio-threads-livekit).

VAD output is not a boolean you branch on once. It is a stream of
speech/silence with hysteresis, so a 40ms click does not count as a turn and
a 40ms dip inside a word does not count as a stop.

The knobs that actually change behavior in LiveKit's Silero plugin:

| Knob | What it does | If you get it wrong |
| --- | --- | --- |
| `activation_threshold` | Probability a frame counts as speech | Too high: misses soft talkers. Too low: TV is a caller |
| `min_speech_duration` | Ignore blips shorter than this | False starts on noise |
| `min_silence_duration` | How long quiet must last before "speech ended" | Too short: chops words. Too long: lag |
| `prefix_padding_duration` | Audio kept *before* speech start | First consonant of the utterance gets eaten |
| `max_buffered_speech` | Cap on the rolling speech buffer | Memory vs catching a long monologue |

LiveKit's turn detector wants `min_silence_duration` of at least **0.25s**.
Go shorter and the semantic model is starved of the pause it uses as a
feature. Go much longer and you have reintroduced the "um" problem VAD
cannot solve.

Prewarm the model in the job process so the first caller of a worker does not
pay ONNX load:

```python
def prewarm(proc: JobProcess):
    proc.userdata["vad"] = silero.VAD.load()

server.setup_fnc = prewarm
```

Then pass `vad=ctx.proc.userdata["vad"]` into `AgentSession`. Loading Silero
per call is how you add 300–800ms of mystery latency to "hello."

The [workshop's turn-detection lesson](https://worksh.app/tutorials/livekit-voice-agent/semantic-turn-detection)
is blunt about this: VAD spots human-patterned audio; humans pause, restart,
and trail off. A semantic detector looks at the *meaning* of the sentence as
well.

"I'd like a room for the —" is incomplete. The words say so. A 700ms pause
after it is still the same turn.

"I'd like a room for the 14th." is complete. A 200ms pause after it is
already late if you wait for VAD silence plus a fixed 500ms pad.

That is why LiveKit layers a **turn detector** on top of VAD. The current
default is an audio+text model (`inference.TurnDetector`) that scores end-of-
turn from acoustics *and* the partial transcript. The older multilingual
text model is still around; same job, transcript-only.

Cost of the extra model: on the order of **~20ms**. Cost of skipping it: the
agent jumps every time someone breathes.

## Four ways LiveKit will decide the turn is over

From the [turns overview](https://docs.livekit.io/agents/logic/turns/):

| Mode | Who decides "done" | Use when |
| --- | --- | --- |
| Turn detector (default) | LiveKit model on audio + text, plus VAD | Almost every STT-LLM-TTS agent |
| VAD only | Silence heuristics | Lowest extra latency, or a language the model misses |
| STT endpointing | AssemblyAI / Deepgram Flux / similar | You already trust that STT's end-of-utterance |
| Realtime LLM | The model's server VAD | OpenAI Realtime, Gemini Live |
| Manual | You | Push-to-talk, IVR-style |

STT endpointing is easy to double-count. If AssemblyAI is already emitting
end-of-utterance, set `turn_detection="stt"` and let VAD handle
*interruptions* only. Running semantic turn detection *and* STT endpointing
*and* a long `min_endpointing_delay` is how you get a polite agent that
takes a second and a half to notice you finished.

Endpointing delay is the last gate, after whoever you picked has said "done":

- `min_endpointing_delay` — never reply faster than this after the signal
- `max_endpointing_delay` — never wait longer than this
- Dynamic endpointing (Python) — stretch the wait when this caller has been
  pausing a lot

You are trading interruptions against lag. There is no default that is
correct for both a fast-talking support line and a hospital switchboard.

## Interruptions are a different VAD problem

Turn-taking is "when do I start." Interruption is "when do I stop."

Naive barge-in: any VAD speech while the agent is talking → cancel TTS.
That also cancels on *"uh-huh"*, *"right"*, and a cough. The caller was
signaling attention, not grabbing the floor.

[Adaptive interruption handling](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/)
runs after VAD and asks whether the new audio is a real barge-in. Brief
backchannels pass through; a full overlapping sentence does not.

The other knobs, if you stay on heuristics:

- `min_interruption_duration` — ignore sub-200ms blips
- `min_interruption_words` — wait until STT has actual words, not just energy
- `false_interruption_timeout` — resume the agent if the "interruption" died

Echo cancellation belongs here too. If the agent's own voice leaks into the
mic, VAD will barge-in on itself. Fix the inbound track (BVC, AEC) before
you tune interruption thresholds. Thresholds cannot unhear a speakerphone.

## What to take into the next piece

VAD gives you a speech mask. Turn detection gives you permission to reply.
Neither transcribes.

STT still has to turn those frames into tokens without adding the 400ms you
just saved, and TTS has to start making sound before the LLM has finished
the paragraph. That pipeline — partials, finals, time-to-first-byte, cancel
on barge-in — is
[STT and TTS streaming](/articles/stt-tts-streaming).
