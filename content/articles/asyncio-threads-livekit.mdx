`async def` is not parallelism. It is a polite queue.

One thread runs an event loop. When you `await` a websocket recv, the loop
is free to flush the next 20ms of TTS. When you call a 25ms ONNX model
*directly*, the loop is stuck. Frames queue. Barge-in is late. The caller
talks over an agent that has not noticed yet.

Voice agents need concurrency in three different senses, and Python gives
you a different tool for each:

| Need | Tool | If you skip it |
| --- | --- | --- |
| Overlap I/O (STT ws, LLM stream, TTS ws) | `asyncio` on one loop | Sequential 1.4s turns |
| Run CPU inference without stalling media | threads / inference process | Late VAD, late barge-in |
| Isolate one bad call from the rest | subprocess per job | One traceback kills the worker |

LiveKit's Agents SDK is mostly an opinionated arrangement of those three.
The [job lifecycle docs](https://docs.livekit.io/agents/server/job/) describe
the process model. This piece is why that model exists, and what you still
have to get right inside `entrypoint`.

## The loop can wait. It cannot think.

Take Silero. [Part 2](/articles/vad-vs-turn-detection) put it on every
audio frame. ~20ms of C++/ONNX, fifty times a second, plus turn-detector
inference on the side.

If that runs on the event-loop thread:

```python
# Looks harmless. Stalls media.
prob = silero_session.run(frame)   # 20ms CPU, GIL / core busy
await stt.push(frame)              # runs late, every time
```

Even when ONNX releases the GIL, *your thread* is inside the call. The loop
cannot publish TTS, cannot read the STT websocket, cannot notice the
cancellation that just arrived.

The fix is old:

```python
prob = await asyncio.to_thread(silero_session.run, frame)
```

LiveKit does the equivalent for you. Local end-of-turn audio prediction in
the agents repo is literally `await asyncio.to_thread(self._eot.predict, pcm)`.
Azure STT cleanup, file checks — same pattern. The rule is boring and
non-negotiable: **CPU or sync SDK → thread. Network → await.**

A tool that does this is a production incident:

```python
@function_tool
async def book_room(self, payload: Booking) -> str:
    return requests.post(HOTEL_URL, json=payload).text  # blocks the loop
```

The function is `async`. The body is not. TTS playout shares that loop.
You just introduced a hitch the size of your hotel API's p95.

Either use `aiohttp` / `httpx.AsyncClient`, or wrap the sync client:

```python
@function_tool
async def book_room(self, payload: Booking) -> str:
    return await asyncio.to_thread(sync_book, payload)
```

LiveKit also hands you `http_context.http_session()` — a shared async
session bound to the job, pooled, closed on shutdown. Use it. Do not
create a new `ClientSession` per tool call, and do not reach for
`requests` because it is what the hotel's sample snippet used.

## Why a thread is not a job

Threads share memory, the GIL, and fate. One leaked native audio callback,
one `os._exit` inside a plugin, one runaway allocation — the worker is
gone, and every other live call on that box dies with it.

So LiveKit's default `JobExecutorType` is **`PROCESS`**.

When a participant joins, the worker assigns an **idle child process** and
runs your `entrypoint` as that process's main coroutine. When the room
empties, shutdown hooks run (10s default), then the process dies. A crash
is a crash of *that call*.

There is a `THREAD` executor. It starts faster and shares the parent
memory. Use it for local experiments. Do not use it as your production
isolation story.

The other process you cannot see from `agent.py` is the **inference
executor**. Loading Silero and the turn detector into *every* job is
wasteful and slow. LiveKit can park ONNX in a dedicated inference process
and RPC to it from jobs. Same reason browsers put GPU work out of the UI
thread: the media loop stays a media loop.

## Prewarm is not optional if you care about the first "hello"

A cold job that loads Silero on first frame pays hundreds of milliseconds
you will never see in a steady-state benchmark. The worker therefore keeps
a pool of idle processes, and you get a `prewarm` hook:

```python
def prewarm(proc: JobProcess):
    proc.userdata["vad"] = silero.VAD.load()

server.setup_fnc = prewarm

@server.rtc_session()
async def entrypoint(ctx: JobContext):
    session = AgentSession(
        vad=ctx.proc.userdata["vad"],
        # stt, llm, tts...
    )
    await session.start(agent=Assistant(), room=ctx.room)
```

Idle pool size scales with CPU by default (`num_idle_processes`). Too few
and a traffic spike forks cold processes in front of living callers. Too
many and you are holding RAM for ONNX copies that are sitting still. This
is the actual capacity knob for a voice fleet — not "number of asyncio
tasks."

`download-files` before deploy is the sibling of prewarm: get the model
weights onto disk in the image, not on the first job.

`asyncio.create_task` is how you overlap. The SDK already does this for the
pipeline. Your job is to not undo it:

- No `time.sleep`. `await asyncio.sleep`.
- No sync disk in a tool. `asyncio.to_thread` or a real async driver.
- No `while True: process(frame)` without an `await` inside. That is a
  spin lock on the media clock.
- CPU-heavy post-call work (write a transcript dump, build a recording)
  belongs in a shutdown hook — and even then, keep it under
  `shutdown_process_timeout`, or hand it to a queue outside the job.

`SpeechHandle` looks like a Future because it *is* one: the loop needs a
single place to cancel playout, TTS, and the LLM together. That is the
barge-in story from [part 3](/articles/stt-tts-streaming), expressed as
scheduling rather than audio.

## Console vs room is a different I/O story, same rule

`uv run agent.py console` reads the mic locally and skips LiveKit Cloud.
Useful. It still runs an asyncio loop, still loads VAD, still dies if you
block. The workshop's console path is how you hear sequential vs streaming
on your laptop. It is not a different concurrency model.

Once you are in a room, add the process boundary. Log `job_id` and
`process_id` (`ctx.log_context_fields`). When barge-in is late, you want
to know whether you blocked the loop or ran out of idle processes.

## The series, collapsed to one sentence

WebRTC gives you a 20ms clock. VAD masks speech on that clock. Turn
detection decides whose clock it is. STT and TTS stream so the gap between
turns stays under half a second. Asyncio overlaps the I/O; threads and an
inference process keep CPU off the loop; a job process keeps one bad call
from taking the box.

The [hotel receptionist tutorial](/tutorials/livekit-voice-agents) is what
you write *after* this: tasks and a TaskGroup, not a second state machine.
The internals are the reason that state machine can run in real time at
all.

If you want the short, opinionated version of why the demo lies, start at
[the hard problems](/articles/voice-agents-hard-problems) and come back
here when you need to know which process to blame.
